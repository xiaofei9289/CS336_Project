#### 2. 各部分具体在学什么

##### 1. 性能测量：先看清楚程序在做什么

这里有两个容易混淆的概念：

- **Benchmarking（基准测试）**：回答“一次前向或训练步骤花多久？”
- **Profiling（性能剖析）**：回答“这些时间和显存具体花在什么地方？”

你要测量前向传播、反向传播和优化器更新，并使用 **NVIDIA Nsight Systems** 查看 CPU 与 GPU 的执行时间线。

这一部分还包括：

- 比较不同模型大小和序列长度。
- 观察预热对测量结果的影响。
- 比较 FP32 与混合精度。
- 分析显存随训练阶段变化的情况。

**学习重点：测出来的时间，需要能说明它代表什么。**例如，GPU 是异步执行的，CPU 发出计算请求所花的时间，与 GPU 完成计算所花的时间不同。

##### 2. 单卡显存：为什么反向传播需要保留这么多东西？

训练过程中，除了参数，还会保存供反向传播使用的中间结果。

这里的 **Activation Checkpointing（激活检查点）**，指的是少保存一部分中间结果，在反向传播需要时重新计算。它与“把训练进度保存到磁盘”不是同一个概念。

作业让你分析：

- 保存中间结果为什么占显存。
- 重计算如何改变显存需求与计算量。
- 在不同重计算限制下，如何比较检查点安排。
- 理论分析是否与实测峰值显存一致。

**学习重点：省显存通常有代价，必须同时关注计算开销。**

##### 3. FlashAttention-2：理解 Attention 的硬件成本

这是作业中较大的实现部分。

普通 Attention 会产生随序列长度平方增长的注意力矩阵。序列变长后，这些中间张量的存储和搬运会变得昂贵。

这一章要求你：

- 测量普通 PyTorch Attention 的时间和显存。
- 比较 `torch.compile` 带来的变化。
- 实现 PyTorch 版本的 FlashAttention-2 前向。
- 实现 Triton 前向 kernel，并支持因果遮罩。
- 完成反向传播及正确性测试。
- 比较不同长度、维度和精度下的性能。

**这份版本的必做反向使用 PyTorch 和 `torch.compile`；Triton 反向在第 4.2.3 节明确标为可选。**

其中，**kernel** 可以理解为 GPU 上执行的一段计算程序；Triton 是编写这类程序的工具。

**学习重点：数学运算相同，数据的存放位置与搬运方式也会显著影响速度。**

##### 4. DDP：让多张 GPU 一起训练

**DDP（Distributed Data Parallel）** 的基本含义是：每张 GPU 保留完整模型，处理不同的数据，再同步梯度。

这一章从基础分布式通信开始，逐步研究：

- 通信本身需要多少时间。
- 基础 DDP 的行为与性能。
- 通信调用次数对性能的影响。
- 通信与反向计算重叠时，训练时间如何变化。

**学习重点：多一张 GPU 增加了算力，也增加了协调成本。**因此，两张卡不一定带来两倍速度。

##### 5. 优化器状态分片：减少重复存储

AdamW 除了使用参数与梯度，还要维护优化器状态，例如动量统计量。

基础 DDP 下，每张 GPU 都保存这些状态的完整副本。**优化器状态分片**让不同 GPU 分担这部分存储。

作业要求实现相应封装，并测量：

- 各训练阶段的峰值显存。
- 每次迭代的耗时。
- 参数、梯度、优化器状态分别占多少空间。
- 与讲义所引用的 ZeRO Stage 1 有何区别。

**学习重点：要能把训练显存拆成不同组成部分，解释优化究竟节省了哪一部分。**

##### 6. FSDP：进一步分担模型状态

**FSDP（Fully Sharded Data Parallel）**进一步把参数、梯度和优化器状态分片存储。

它带来的新问题是：计算某一层时，需要的完整参数可能分散在其他 GPU 上。因此，参数的通信、使用与释放时机都很重要。

这一部分包含：

- FSDP 封装与正确性测试。
- 混合精度相关要求。
- 显存节省分析。
- 使用 Nsight 检查通信是否及时完成。

**学习重点：显存占用与通信开销紧密相关，需要一起考虑。**

##### 7. 并行策略分析：什么时候加卡不再有效？

这一章主要是数学分析，研究：

- 数据并行 DP。
- 完全分片数据并行 FSDP。
- 张量并行 TP。
- FSDP 与 TP 的二维组合。

你要比较各策略的**计算量与通信成本**，判断何时通信会成为瓶颈。

直观地说：如果每张 GPU 的计算工作已经很少，却仍要等待大量数据交换，继续加卡的收益就会下降。

##### 8. Leaderboard：把前面的知识合起来

这份讲义的排行榜测量的是 **8B 模型的完整训练步骤**，包括前向、损失、反向与 AdamW 更新。

指定场景包括：

- 两张 B200 GPU。
- Batch size 为 2。
- 序列长度为 32,768。
- BF16 与因果遮罩。

**这一部分检验的是端到端效果：局部算子变快，最终是否让整个训练步骤变快。**

#### 3. 2.1.3：端到端计时——你的第一个正式任务

这一节对应 **`benchmarking_script`，4 分**。

##### 3.1 首先分清三个训练阶段

**前向传播 Forward**

输入经过模型，产生预测结果。训练时，还会基于预测计算损失。

**反向传播 Backward**

利用链式法则，计算损失对模型参数的梯度。

**优化器更新 Optimizer step**

优化器根据梯度及自身维护的状态更新参数。

因此，以下指标不是同一个东西：

| 指标             | 含义                                       |
| ---------------- | ------------------------------------------ |
| 仅前向耗时       | 只测前向部分                               |
| 前向加反向耗时   | 测两个阶段合计                             |
| 完整训练步骤耗时 | 包含前向、损失、反向及优化器更新等约定工作 |

**“测了前向加反向”不等于“已经单独测出了反向耗时”。**报告时，必须说明每个数字覆盖哪些工作。

另外，“只执行前向”也不能自动说明是否关闭了梯度记录。有没有记录计算图，会影响执行与显存行为，需要明确实验设置。

##### 3.2 为什么 GPU 计时容易出错？

关键原因是：**CUDA 操作通常是异步提交的。**

可以把 CPU 想成派发任务的人，把 GPU 想成执行任务的人：

> CPU 把任务交给 GPU 后，可以继续派发后面的任务，不必等前一个任务完成。

所以，CPU 上某次函数调用返回，只说明它完成了相应的提交工作，未必说明 GPU 已经算完。

如果计时范围只覆盖 CPU 提交任务的过程，你测到的就可能不是想要的 GPU 执行时间。

讲义因此要求在每个步骤后调用 `torch.cuda.synchronize()`。概念上，它让 CPU 等待 GPU 上已提交的相关工作完成。

这里的“同步”是 **CPU 与 GPU 执行进度的同步**，还不是后面多卡训练的梯度同步。

##### 3.3 为什么需要预热？

一次程序运行中，最初几次执行与后续执行可能处于不同状态：有些资源、缓存或运行时组件需要首次建立。

**预热的目的，是让正式测量更接近持续运行时的状态。**

但这道题要求你亲自比较不同预热次数，所以不要提前把某个原因当成实验结论。应结合实际结果判断：变化集中在哪里，是否稳定，少量预热是否足够。

##### 3.4 为什么同时报告平均值和标准差？

假设两个实验平均耗时相同：

- 实验 A 每次耗时都很接近。
- 实验 B 有时很快，有时很慢。

它们的稳定性不同。

- **平均值**概括典型耗时。
- **标准差**描述测量的离散程度。

标准差明显偏大时，单凭平均值比较两个实现，结论可能不可靠。

##### 3.5 这一题要求交什么？

题目分三部分：

1. **脚本**：支持模型配置、随机数据、可配置预热与测量次数，以及三种执行模式。
2. **正式计时**：按给定模型配置，使用 **5 次预热、10 次测量**，报告平均值和标准差。
3. **预热对比**：比较不预热、预热 1 次、预热 2 次时的结果，并解释观察。

本节的核心能力是：**能准确说清楚“这个时间到底测了什么”。**

#### 4. 2.1.4：Nsight Systems——把总耗时拆开看

这一节对应 **`nsys_profile`，5 分**。

##### 4.1 为什么有计时脚本还不够？

计时脚本可能告诉你：

> 一次前向需要这么多毫秒。

但它无法解释：

- 哪些算子最耗时？
- GPU 是否一直在工作？
- CPU 提交任务与 GPU 执行之间是什么关系？
- 很多小操作是否积累了可观的开销？

Nsight Systems 用时间线和统计表帮助你观察这些问题。

##### 4.2 Python 操作与 GPU kernel 是什么关系？

**Kernel 是在 GPU 上执行的一段计算程序。**

一个 Python 层面的操作可能触发多个 kernel；经过编译或融合后，多个高层操作也可能由一个 kernel 完成。

因此：

> Python 函数名称、模型模块名称和 GPU kernel 名称，并不总是一一对应。

这也是为什么普通 Python profiler 不足以描述 GPU 内部执行情况。

##### 4.3 如何理解 Nsight 时间线？

可以关注三种信息：

| 信息              | 你能从中看到什么                       |
| ----------------- | -------------------------------------- |
| CPU/CUDA API 活动 | CPU 什么时候提交任务、等待或调用运行时 |
| GPU kernel 活动   | GPU 什么时候执行哪些计算               |
| NVTX 标记         | 这些活动对应模型的哪个逻辑阶段         |

**NVTX 可以理解为给程序的不同阶段贴标签。**

例如，讲义希望区分前向、反向，以及 Attention 内的不同计算部分。这些标签有助于把底层 kernel 对应回模型逻辑，也便于排除预热阶段。

##### 4.4 几种“时间”不要混淆

- **一次 kernel 的耗时**：单次调用持续多久。
- **某类 kernel 的累计耗时**：这种 kernel 的多次执行累计多久。
- **整个阶段的墙钟时间**：从阶段开始到结束实际经过多久。

一个很短但被调用很多次的 kernel，也可能占据较高的累计时间。

同时，整个阶段的墙钟时间与所有 kernel 耗时之和不一定相同，因为还涉及空隙、等待，以及可能发生的执行重叠。

##### 4.5 为什么 FLOPs 多，不一定耗时占比就大？

**FLOPs 是浮点运算次数，耗时是实际执行时间。**

实际时间还受到这些因素影响：

- 数据搬运。
- 算子能够达到的硬件计算效率。
- kernel 启动开销。
- 同步与等待。

因此，不能只根据 FLOPs 占比判断哪些操作值得关注。题目要求你通过 profile 比较，而不是预先指定一个“最慢的算子”。

#### 5. 2.1.5：混合精度——速度与数值表示的关系

本节有两道题：

- `mixed_precision_accumulation`：1 分。
- `benchmarking_mixed_precision`：2 分。

##### 5.1 浮点数的两个维度：范围与精细程度

理解浮点格式时，要分清：

- **数值范围**：能表示多大、多小的数。
- **表示精度**：在某个数附近，能区分多小的差别。

| 格式 | 存储位数 | 指数位数 | 尾数字段位数 |
| ---- | -------- | -------- | ------------ |
| FP32 | 32       | 8        | 23           |
| FP16 | 16       | 5        | 10           |
| BF16 | 16       | 8        | 7            |

上表未单列的 1 位是符号位。

这意味着：**BF16 与 FP16 都占 16 位，但它们的数值特性不同。**BF16 的指数范围与 FP32 接近，表示精细程度则更低。

##### 5.2 为什么低精度可能更快？

主要有两方面：

- 每个元素占用的存储更少，可能减少数据传输量。
- GPU 的 Tensor Cores 可以加速支持的低精度矩阵运算。

但这不意味着整个模型一定按同样比例加速。完整程序还有其他运算、数据转换和调度开销。

因此，本节要你测量不同模型大小下的变化。

##### 5.3 什么叫“混合精度”？

同一次模型计算中，不同操作可以采用不同精度。

要区分三个问题：

1. 参数以什么 dtype 存储？
2. 某个操作用什么 dtype 执行、输出？
3. 累加过程用什么精度？

它们不必完全相同。

讲义介绍的 `autocast` 会根据操作采用相应的精度策略。**不能把进入 autocast 理解成“整个模型永久变成某一种低精度格式”。**

##### 5.4 累加实验想让你理解什么？

讲义给出了多组反复累加小数的实验。

它希望你区分：

- 小数最初被表示时产生的误差。
- 反复相加时，每一步舍入产生的误差。
- 累加器精度与输入精度的区别。

一个有帮助的概念是：**把已经舍入的数转换到更高精度，不会自动找回丢失的信息。**

具体哪组实验得到什么结果、误差如何比较，需要你运行并观察；这些就是题目要求分析的内容。

##### 5.5 ToyModel 题为什么要逐层观察 dtype？

题目要求你检查参数、线性层输出、LayerNorm 输出、logits、loss 和梯度。

这是为了让你认识到：**混合精度需要沿着计算过程理解，不能只看输入或模型参数的 dtype。**

还要注意，题目中的 ToyModel 使用 LayerNorm，而你在 Transformer 中熟悉的可能是 RMSNorm，分析时应看清具体操作。

#### 6. 2.1.6：显存分析——看张量的生命周期

这一节对应 **`memory_profiling`，4 分**。

##### 6.1 训练显存由哪些部分组成？

| 类别                 | 作用                         |
| -------------------- | ---------------------------- |
| 参数                 | 模型当前的权重               |
| 梯度                 | 损失对参数的导数             |
| 优化器状态           | 优化器维护的历史统计量       |
| 激活与保存的中间张量 | 为后续运算或反向传播提供数据 |
| 临时张量和工作空间   | 计算过程中临时使用的空间     |

**模型参数大小不能代表训练峰值显存。**

同样，结束时占用多少显存，也不能代表执行过程中最多用了多少。

##### 6.2 为什么要看“时间线”？

显存是随时间变化的：

- 某个张量被创建。
- 它被后续操作使用。
- 当不再需要时，其空间可以被释放或复用。

反向传播期间，一些前向保存的张量会被释放，同时又会产生梯度。因此，不能只看一条曲线下降多少，就直接认定释放了多少前向激活。

你需要把**分配、释放、阶段切换**联系起来解释。

##### 6.3 PyTorch Memory Profiler 提供什么？

讲义让你记录显存分配历史，生成 snapshot，再用 `memory_viz` 查看。

它能帮助观察：

- 某一时刻有哪些活跃分配。
- 每块分配有多大。
- 分配持续了多久。
- 调用栈指向哪里的操作。

与“进程总共占用多少 GPU 显存”相比，这些信息更适合定位来源。

##### 6.4 两组容易混淆的概念

**活跃张量内存与缓存预留内存**

PyTorch 可以保留已申请的显存块供后续复用。因此，“当前张量使用的空间”和“分配器保留的空间”不是同一指标。

**Residual stream 与反向保存的 residuals**

- **Residual stream**：Transformer 残差路径上传递的隐藏表示。
- **Autograd residuals / saved tensors**：为反向传播保存的中间张量。

本章两种含义都会出现，要根据上下文区分。

##### 6.5 这一题要求做什么？

指定使用 **xl 模型**，上下文长度为 **128 和 2048**，研究：

1. 仅前向与完整训练步骤的显存时间线。
2. 两种长度下的峰值显存。
3. 混合精度对峰值显存的影响。
4. 残差流中激活张量的大小，并换算为 MiB。
5. 最大分配来自哪里。
6. 单个 Transformer block 为反向保存了多少数据，最大的五类贡献来自哪些操作，以及反向生成梯度的内存开销。

交付材料包含时间线截图、峰值表格、Nsight 截图，以及自己的推导和解释。
