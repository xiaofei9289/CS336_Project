这份文件主要是 **作业 2 的第 2 章：性能测试与分析（Profiling and Benchmarking）**，最后接了第 3 章的开头。

你可以先抓住一句话：

> **让一个 Transformer 跑起来，测清楚它“哪里慢、哪里占显存”，再判断应该优化什么。**

这一部分主要研究运行效率，所以**可以使用随机参数、随机输入，不需要先训练出一个效果好的模型**。

**1．先理解：你到底在测什么？**

一次完整的训练步骤，可以拆成下面几个部分：

| 阶段                      | 在做什么                   | 小白理解                   |
| ------------------------- | -------------------------- | -------------------------- |
| 前向传播 Forward          | 输入经过模型，得到预测结果 | 模型做题                   |
| 计算损失 Loss             | 比较预测结果和目标         | 看错了多少                 |
| 反向传播 Backward         | 计算损失对各参数的梯度     | 判断参数应该往哪个方向调整 |
| 优化器更新 Optimizer step | 用梯度更新参数，例如 AdamW | 实际修改参数               |

这几个阶段都会消耗**时间和显存**。

作业要你从三个角度研究它们：

| 角度     | 你想回答的问题                       | 使用的方法                 |
| -------- | ------------------------------------ | -------------------------- |
| 总体计时 | 前向、反向、更新，各要多久？         | Python 计时脚本            |
| 计算分析 | 时间具体花在哪些 GPU 运算上？        | NVIDIA Nsight Systems      |
| 显存分析 | 显存什么时候最高？哪些张量占得最多？ | PyTorch memory profiler 等 |

**总体计时相当于看“整场考试用了多久”，性能分析则是看“每道题分别用了多久”。**

**2．第一块：建立一套可重复使用的测试脚本**

对应 **2.1.1—2.1.3**。

先加载作业 1 的 Transformer。可以使用作业提供的参考实现，也可以使用自己的实现。

然后写一个测试脚本，让它能够：

1. 根据配置创建模型。
2. 生成随机输入。
3. 先运行几步预热。
4. 正式运行多步，记录时间。
5. 输出平均耗时和标准差。

脚本需要支持三种模式：

| 模式       | 执行内容                              |
| ---------- | ------------------------------------- |
| 只前向     | Forward                               |
| 前向＋反向 | Forward → Loss → Backward             |
| 完整训练步 | Forward → Loss → Backward → Optimizer |

这里有两个核心概念。

**① 为什么要预热？**

第一次运行可能包含一些额外准备工作，例如初始化、内存分配以及底层计算库的准备。

所以：

> 第一次跑得慢，不一定意味着模型正常运行时也这么慢。

作业要求先用 **5 步预热＋10 步正式测量**，再与不预热、预热 1 或 2 步进行比较。

**② 为什么要 `torch.cuda.synchronize()`？**

CPU 把任务交给 GPU 后，可以先继续执行后面的代码，不一定等 GPU 做完。

如果直接停止计时，可能测到的是：

> CPU 提交任务用了多久。

而你真正想测的是：

> GPU 完成这些计算用了多久。

因此，计时需要配合同步，作业明确要求每步结束后同步。

这一块最终产出：**一个后续章节反复使用的测试脚本，以及耗时统计与简短解释。**

**3．第二块：用 Nsight 找出时间花在哪里**

对应 **2.1.4**。

假设你已经测出：

> 一次前向传播需要 100 ms。

现在还不知道这 100 ms 里：

- 矩阵乘法用了多少？
- Softmax 用了多少？
- 归一化用了多少？
- GPU 是否有空闲等待？

**Nsight 就是用来把这些细节拆开的。**

你会看到很多 **CUDA kernel**。可以先把 kernel 理解成：

> GPU 上执行的一段具体计算程序，例如一次矩阵乘法，或一组逐元素运算。

注意：**一个 Python 运算不一定只对应一个 kernel。**

作业要求选择 **两种模型大小、三种大于 128 的二次幂序列长度**进行分析；其中最大的序列长度要选显存能容纳的最长长度。通常整理成六组组合。

每组主要回答：

| 要研究的问题                                            | 背后的目的                       |
| ------------------------------------------------------- | -------------------------------- |
| Nsight 的前向时间和 Python 测量是否一致？               | 检查计时口径及分析工具的额外开销 |
| 哪个 kernel 累计耗时最多？调用几次？                    | 找出主要耗时来源                 |
| 除了矩阵乘法，还有哪些操作很耗时？                      | 找到容易忽视的瓶颈               |
| 完整训练相比只前向，矩阵乘法占比如何变化？              | 理解反向和优化器增加了什么工作   |
| 注意力中的 Softmax 与矩阵乘法，耗时和计算量是否成比例？ | 理解“计算量少”不等于“耗时一定少” |

这里的 **NVTX 标签**，可以理解为给时间轴贴标签：

```
with nvtx.range("forward"):
    ...
```

这样你就能识别“这一段属于前向”，并把预热与正式测量区分开。

这一块想让你建立的认识是：

> **程序速度不仅取决于做了多少次运算，也取决于数据搬运、GPU 利用率、任务启动等因素。**

**4．第三块：换一种数值精度，看看能不能更快**

对应 **2.1.5：混合精度**。

你可以把 FP32、FP16、BF16 看作不同的数字存储格式：

| 格式 | 每个数占用空间 | 主要特点                          |
| ---- | -------------- | --------------------------------- |
| FP32 | 4 字节         | 表示更精细，但存储开销较大        |
| FP16 | 2 字节         | 适合加速部分计算，但表示范围较小  |
| BF16 | 2 字节         | 表示范围接近 FP32，但有效精度较低 |

混合精度的想法是：

> **适合低精度的运算用低精度，需要更高精度的地方保留高精度。**

它不是简单地把所有东西都改成 BF16。

这一节分三步：

- **累加小实验**：把 `0.01` 加 1000 次，观察不同精度的误差。
- **小模型分析**：观察参数、各层输出、损失和梯度分别是什么数据类型。
- **真实模型测速**：给测试脚本增加 BF16 混合精度选项，与 FP32 比较。

累加实验是在解释一个重要现象：

> 小误差反复积累后可能变得明显，所以“输入使用低精度”和“累加也使用低精度”是两回事。

最终你需要回答：**混合精度加速了多少？不同模型大小下，效果是否相同？**

**5．第四块：研究显存为什么会被占满**

对应 **2.1.6：显存分析**。

先把训练中常见的显存占用分清：

| 类别                   | 含义                                     | 举例                       |
| ---------------------- | ---------------------------------------- | -------------------------- |
| 参数                   | 模型当前的权重                           | 各层的权重矩阵             |
| 激活及为反向保存的张量 | 处理当前输入时产生、后续计算还需要的数据 | 中间层输出、某些运算的输入 |
| 梯度                   | 损失对参数等张量的导数                   | 权重对应的 `.grad`         |
| 优化器状态             | 优化器保存的历史信息                     | AdamW 的一阶矩、二阶矩     |
| 临时张量               | 某些运算临时需要的空间                   | 中间计算结果               |

**激活可以理解成模型做题时产生的中间结果。**
 为了反向传播，系统会保留其中一些结果，或保留计算导数需要的其他张量。

所以显存不是“模型加载以后就固定了”，而是会随着执行阶段不断变化。

这部分主要使用 **xl 模型、序列长度 128 和 2048**，研究：

- 只做前向和完整训练，显存曲线有什么不同？
- 各自的峰值显存是多少？
- BF16 混合精度能减少多少显存？
- 最大的内存分配来自哪个操作？
- 一个 Transformer Block 为反向保存了多少数据？
- 反向释放保存张量的同时，又产生了多少梯度数据？

还会让你进行简单的理论估算。例如，一个形状为：

$[B,T,d_{\text{model}}]$

的 FP32 激活张量，占用：

$B\times T\times d_{\text{model}}\times4\ \text{字节}$

其中 $B$ 是 batch size，$T$ 是序列长度。

**这一块是在把“显存曲线上的峰值”和“代码里实际创建的张量”对应起来。**

注意两个术语：

- **Residual stream**：Transformer 残差连接主路径上的表示。
- **Autograd residuals / saved tensors**：为反向传播保存的张量。

虽然都出现 residual，但这里含义不同。

**6．这些内容怎样连接到后面的优化？**

你可以按下面这张表理解整份作业的推进逻辑：

| 阶段               | 核心问题                           | 对应方向                         |
| ------------------ | ---------------------------------- | -------------------------------- |
| 先测总体表现       | 到底有多慢？                       | Benchmark                        |
| 再定位原因         | 哪些运算慢、哪些张量占显存？       | Profiling                        |
| 调整数值精度       | 能否更快、少存一些数据？           | Mixed precision                  |
| 减少保留的中间结果 | 能否少占显存，代价是什么？         | 第 3 章 Activation checkpointing |
| 改进注意力实现     | 能否减少数据搬运，提高运行效率？   | 后续自定义 GPU kernel            |
| 使用多张 GPU       | 如何分担计算、存储，以及处理通信？ | 后续多 GPU 训练                  |

其中第 3 章的 checkpointing，可以先理解为：

> **部分中间结果先不保存，等反向传播需要时重新计算，用额外计算换显存。**

因此，你现在读这一章时，先围绕四个问题建立框架就够了：

1. **测什么？** 前向、反向、优化器的时间和显存。
2. **怎么测准？** 预热、同步、多次测量、统一口径。
3. **为什么慢、为什么占显存？** 用工具定位到具体运算和张量。
4. **怎样证明优化有效？** 在相同条件下，比较优化前后的结果。
